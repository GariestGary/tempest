## Safety

- VORTEX is the TEMPEST production host. Read-only SSH audits, TEMPEST diagnostics, service-state checks and log review are allowed. Installing, updating and maintaining TEMPEST there are allowed only with explicit owner authorization for the operation. Before any production mutation, make protected backups and prepare rollback; keep secrets, private keys and user data out of Git and logs.
- An authorized TEMPEST deployment may autonomously perform its necessary scoped steps, including container build/update and TEMPEST systemd unit replacement when authorized. Do not reboot VORTEX. Changes to third-party services, host firewall, system routing, or a running dataplane require separate authorization. Do not apply a network plan or restart dataplane unless explicitly necessary and separately authorized.
- Do not take over host networking, use privileged PiTun Compose, expose the host Docker socket to Web/API, grant broad Web/API privileges, or make host-wide DNS, route or firewall changes. Validate before Apply, preserve protected LKG, and fail closed if safe rollback is impossible.
- DIRECT requires explicit rules. Geo-specific routing is manual. AUTO uses transport health and explicitly approved candidates. Do not implement automatic detection of content geoblocking.
- Experimental development and potentially dangerous network tests run only in an explicitly approved disposable Linux VM and namespace, never on production VORTEX. On TYPHOON, `ssh lab` may reach Ubuntu VM `tempest-lab-ubuntu` (user `gary`, checkout `~/tempest`). Before any experiment verify guest identity, origin/branch/SHA, target and PID 1 namespaces, recovery snapshot and independent console. Risky mutations require exact selectors and owner authorization. Never mutate the guest host namespace or bypass unavailable lab access.
