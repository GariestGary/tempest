# TEMPEST — готовый userspace dataplane или управление ядром

**Дата** 2026-11-18. Владелец принял результаты A/B на `b35c5de` в проверенных границах, утвердил Xray 26.10.31 для MVP и взял проект редакции этапа 2 за основу. План block + dummy приостановлен. Task 2.6 `IN_PROGRESS`, Gate 2 `OPEN`, ADR-001 `PROPOSED`.

## Вывод

**Движок MVP — Xray 26.10.31 по решению владельца.** В согласованном A/B оба движка провели трафик реального WireGuard-клиента через ручные правила DIRECT/VLESS/BLOCK без capabilities и TUN у gateway. Xray привязал WG к конкретному адресу, явно завершился при коллизии UDP-порта и восстановил рабочий LKG после освобождения порта. sing-box слушал wildcard-адреса, при коллизии оставался жив без WG listener, а первый проверяемый запуск LKG закрыл WG-сокеты. У Xray также можно переиспользовать чистую часть существующего генератора PiTun. [Матрица VM](#результаты-vm-ab) · [Генератор PiTun](../backend/app/core/config_gen.py)

Для проверенного WG ingress и обычного IP egress движок берёт на себя завершение WG, TCP/UDP стек, маршрутизацию по правилам, блокировку и VLESS. Этому профилю не требуются собственные runtime-менеджеры kernel WireGuard, TUN, nftables/TPROXY и IP-маршрутов. Обвязка TEMPEST отвечает за валидацию политики, применение конфигурации, проверку живого пути и восстановление подтверждённого LKG. ## Общий стенд для двух минимальных POC

После отдельного разрешения поднять **один тестовый gateway в disposable Ubuntu VM**, обычный UID, пустые capability masks, `NoNewPrivileges=1`, без устройства `/dev/net/tun`, Docker socket и host networking. Клиент и контролируемые VLESS upstream, DNS и TCP/UDP sink находятся на заранее подготовленных изолированных тестовых сегментах. Существующий `tempest-ns-lab` с одним loopback не предоставляет этих путей. Подготовку транспорта согласовать отдельно и сделать вне TEMPEST. Перед стартом проверить UUID, snapshot, независимую консоль, идентичность namespace, маршруты, селекторы и свободные UDP-порты. Сравнивать движки последовательно на одной топологии, в отдельных процессах и конфигах.

Движок запускается отдельным sandboxed процессом с обычными IPv4/IPv6 сокетами, а существующий IPC unit сохраняет `RestrictAddressFamilies=AF_UNIX`. При необходимости отдельно измерить read-only AF_NETLINK для мониторинга интерфейса. Для конфигурации разрешены только нужные типы listener/outbound и параметры внутри профиля. Кандидат с TUN, `system: true`, `sockopt.mark`, произвольным путём или управляющим TCP API должен отвергаться до запуска. [Текущий IPC unit](../deploy/systemd/tempest-network-agent.service)

|---|---|

### POC A — Xray-first

В отдельном минимальном профиле Xray 26.10.31 поднять `inbounds[].protocol="wireguard"` с тегом `wg-poc`, привязкой к утверждённому адресу VM на UDP 51871, `settings.address` для серверных IPv4/IPv6 и одним `peers[]`. Для контроля egress использовать `freedom` без `sockopt.mark`, VLESS `raw` + TLS и `blackhole` первым outbound. Порядок правил — разрешённый resolver через VPN, запрет остальных DNS/DoT, явные DIRECT и VPN назначения, catch-all WG inbounds → `blackhole`. Для доменного теста включить sniffing с `routeOnly` и точным `full:` правилом. Запустить изолированный конфиг после `run -test`, без полного `generate_config()` и без legacy API старта. Обязательный POC не использует WG outbound. Для отдельного варианта «WG поверх WG» потребуется подтвердить `noKernelTun: true`, dual-stack адреса и отсутствие legacy mark. [WG schema](https://github.com/XTLS/Xray-core/blob/v26.10.31/infra/conf/wireguard.go) · [WG inbound](https://xtls.github.io/en/config/inbounds/wireguard.html)

### POC B — sing-box-first

Поднять sing-box 1.14.2 с `endpoints[].type="wireguard"`, `tag="wg-poc"`, `system=false`, UDP 51872 и теми же серверными префиксами, MTU и peer-ограничениями. Учитывать фактический UDP bind и ограничивать его разрешённой тестовой сетью. Поставить `route` на теги DIRECT/VLESS для тех же разрешённых назначений, явный `reject` в конце, `route.final` на VPN для защиты от неявного DIRECT. Для UDP VLESS указать `packet_encoding: xudp` и проверить XUDP с тем же сервером. Для доменного теста добавить `sniff` до правила. Проверять кандидат `sing-box check -c`, затем штатный restart и revoke peer. Встроенный `hijack-dns` с резолвером `detour: vpn` проверить отдельным вариантом после базового паритета. [WG endpoint](https://github.com/SagerNet/sing-box/blob/v1.14.2/docs/configuration/endpoint/wireguard.md) · [VLESS UDP](https://github.com/SagerNet/sing-box/blob/v1.14.2/protocol/vless/outbound.go)

### Критерии успешного прогона

1. Клиент выполняет WG handshake. TCP и UDP пробы по IPv4 и IPv6 доходят до sink с ожидаемым адресом источника для каждого правила. Проверить UDP echo, малый и близкий к MTU пакет. Ping сам по себе не подтверждает этот контракт. Для смены правила взять новый поток и сверить путь.
2. Остановить только согласованный тестовый VPN upstream. Защищённые TCP/UDP и DNS перестают работать. На прямом пути отсутствуют соответствующие пробам пакеты, хотя контрольная проба подтверждает его достижимость. Явно разрешённый DIRECT продолжает работать. Повторить после восстановления upstream и перезапуска engine. Не переносить PiTun `proxy → direct` при отсутствующем active node, catch-all DIRECT, прямой port 53 или per-resolver DIRECT. [Legacy routing](../backend/app/core/config_gen.py#L638) · [Legacy DNS](../backend/app/core/config_gen.py#L855)
3. Проверить A/AAAA, IPv6 literals, DNS по UDP и TCP, неподтверждённые DNS/DoT назначения. Сопоставить запросы на клиенте, gateway и resolver. `UseIPv4` меняет DNS-ответы, но не закрывает IPv6 по literal, из кеша или при наличии нативного маршрута на клиенте. При полном туннеле проверять оба семейства на физическом uplink клиента. При split tunnel описать, какие назначения имеют право выйти напрямую. Политика клиента при отключении самого туннеля требует отдельного always-on/kill-switch на поддерживаемых платформах. Без него вывод ограничивается установленным тестовым клиентским профилем и серверным dataplane. [WireGuard cryptokey routing](https://www.wireguard.com/#cryptokey-routing)
4. Неправильный peer или отозванный ключ не устанавливают новый доступ. Проверить также судьбу старого TCP/UDP потока. Ошибочный кандидат отвергается до подмены активного файла. При неудачном запуске после валидного кандидата восстановить безопасный тестовый LKG или остановить ingress. Этот тест проверяет свойство, которое будущая транзакция TEMPEST должна обеспечить.
5. Сверить `ip link/address/route/rule`, nftables и разрешённые listeners до и после, а также UID, `Cap*` и `NoNewPrivs` работающего процесса. Должны остаться только заранее согласованный bootstrap и пользовательские UDP/TCP сокеты движков. Изменение PID 1, системных маршрутов, DNS или незапланированный listener означает FAIL. Сохранить адреса источников, исходы проб и версии без приватных ключей.

### Метод проверки

- Bootstrap выполнялся штатными `ip netns` и `ip link/addr/route`. Ubuntu-пакеты WireGuard распакованы `dpkg-deb -x` после сверки SHA-512 с метаданными APT. Использованы `wireguard-tools` из пакета `1.0.20250521-1ubuntu1` и `wireguard-go` из пакета `0.0.20231211-1build1` (бинарник сообщает `v0.0.20230223`). WG handshake сверялся через `wg show tpab-wg latest-handshakes` и захват зашифрованного UDP на `tpab-cg`.
- Gateway запущен через `ip netns exec`, приватный mount namespace и `setpriv --reuid 61126 --regid 61126 --clear-groups --bounding-set=-all --inh-caps=-all --ambient-caps=-all --no-new-privs`. `/proc/<pid>/status`, `/proc/<pid>/ns/{net,mnt}`, видимость устройства и открытые дескрипторы проверены у процесса движка. `ss -lnup` связывает сокет с PID. Bootstrap namespaces и захваты пакетов выполняет привилегированный оператор, TUN нужен процессу тестового клиента.
- TCP/UDP echo проверяет полный ответ с уникальным маркером и фиксирует IPv4/IPv6 источника на sink. DNS-пробы используют `dig -r @<resolver> <unique-name> A|AAAA +short +norecurse +timeout=1 +tries=1` с отдельными `+tcp` и `+notcp`. `tcpdump` наблюдает WG, внешний WireGuard UDP, VLESS/TLS и три различимых выхода. Положительные контрольные пробы до защищённых назначений выполняются обычными сокетами из `tpab-g` под тем же непривилегированным UID. Во время отказов контрольные пробы выделены в отдельные окна захвата.
- Перед заменой файла используется `xray run -test -config` или `sing-box check -c`. Запуск кандидата с конфликтом происходит уже после `fsync` и атомарной замены файла. Восстановление начинается после остановки кандидата, освобождения порта и проверки `ss`. Содержимое подтверждённого файла сверяется побайтово. После запуска LKG проверяются DIRECT, VLESS, DNS и BLOCK реальным трафиком.

### Отказы и границы вывода

- В первой сетевой попытке Xray сделал WG handshake, но стандартное ограничение Freedom закрыло документационные диапазоны на DIRECT и на общем Xray upstream. Контрольные сокеты достигали sink. Добавлены точные `freedom.settings.finalRules` только для адресов назначения, TCP/UDP `18080` и разрешённых resolver-адресов на `53`. Default BLOCK сохранён. В ранней попытке после клиентского `link down` Linux также удалил IPv6-адрес с WG. В повторе тот же адрес восстановлен перед следующей серией проб без изменения sysctl. [Freedom](https://github.com/XTLS/Xray-core/blob/v26.10.31/proxy/freedom/freedom.go) · [Матчер специальных диапазонов](https://github.com/XTLS/Xray-core/blob/v26.10.31/common/geodata/consts.go)
- Серверный fail-closed проверен при действующих default routes через WG на клиенте. В отрицательных окнах в клиентском WG были соответствующие пакеты, а на `tpab-gs` и `tpab-cs` их не было. Повторные контрольные пробы к тем же адресам и resolver прошли по `tpab-gs` во время остановки upstream и отдельно при остановленном gateway. При снятии WG-маршрутов приоритет получил нативный путь клиента. Для защиты при выключении туннеля требуется отдельная политика always-on/kill-switch ОС клиента.
- При первом восстановлении sing-box после освобождения UDP-порта журнал зафиксировал открытие сокетов, затем остановку обоих WG receivers и `missing default interface`, хотя процесс сообщил `started`. В исходниках этого релиза монитор при отсутствии default interface вызывает `NetworkPause`, а WG endpoint переводит устройство в Down и освобождает UDP-сокеты. В двух целевых повторах профиль LKG восстановил VLESS и DNS через тот же upstream, но IPv6 DIRECT по TCP/UDP не дал клиенту ответа. Во втором повторе захват показал TCP SYN и UDP-запрос на прямом veth, sink записал UDP, обратных пакетов на том veth не было. Причина отсутствия обратного трафика не установлена. Default route в gateway не добавлялся, поэтому вывод о восстановлении sing-box ограничен согласованной топологией. ### Контроль окружения и доказательства

В основном A/B подтверждены 217 проверок Xray с учётом повторного разбора PCAP и инвентаризации UDP-сокетов. Для sing-box получены 145 положительных проверок и один отказ запуска LKG. Целевой повтор sing-box завершил дополнительные проверки, включая 12/12 контрольных проб по нативному клиентскому пути, отзыв peer и возврат к WG. В повторе 72 проверки прошли, четыре отказа относятся к двум попыткам запуска LKG и двум пробам IPv6 DIRECT. В 173 основных и 47 дополнительных захватах счётчики потерь ядра равны нулю.

После точечного cleanup остался только исходный `tempest-ns-lab` с loopback. Снимки PID 1 и существующего namespace совпали по interfaces, addresses, routes, rules, nftables, listeners, resolver и boot ID с исключением поля `expires` IPv6 RA. В основном A/B оно изменилось `65358 → 65163`, в последнем повторе `65481 → 65418`. В диагностическом повторе наблюдался также рост RA timer. Модуль `veth` штатно загрузился в ядре гостя при подготовке стенда. Временные процессы, namespaces, интерфейсы, конфиги, ключи и файлы в VM удалены. Сетевые мутации ограничены четырьмя тестовыми namespaces гостя. TYPHOON служил площадкой запуска и доступа к консоли. VORTEX в эксперименте не участвовал.

SHA-256 сохранённых обезличенных сводок. Основной A/B `b8b8a7ad82f28a98af86a91ac35fe8f760b5ea6fab93fcec99e839e14d1fd5e0`. Последний целевой повтор `d6e3eeb86fabdd93e7c844ec8a3c570fddd0afb775d67ecf05fccb2a67245e13`. Сводки содержат первичные оценки, адреса источников sink и счётчики пакетов.
