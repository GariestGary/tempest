# AWG egress — передача на TORNADO, 27.11.2026

## 27.11.2026 · DoT: отказные проверки

Владелец принял доказательство полноценного DNSKEY через реальную AWG-подписку. На подтверждённом generation 37 последовательно испытаны остановка DNS unit, остановка AWG SOCKS и имитация недоступного DoT изменением только адреса его upstream на зарезервированный тестовый адрес. Во всех трёх случаях клиентские DNS TCP/UDP не получили A-ответа, разрешённый DIRECT и BLOCK контроль прошли, а исходящих TCP/UDP DNS/DoT пакетов на `tpab-gu`, `tpab-gs`, `tpab-gw` не обнаружено (по ноль, без потерь capture). После каждого случая штатный recovery вернул LKG 37 и сохранил множество отзывов. Это имитация недоступности endpoint, а не управляемое отключение реального Cloudflare.

Дополнительный отказ AWG подтвердил блокировку клиентских DNS TCP/UDP, HTTPS и UDP, сохранение разрешённого DIRECT и отсутствие наблюдаемого TCP fallback к тестовому HTTPS endpoint (0 исходящих пакетов, без потерь capture). Штатный тест pending rollback вернул подтверждённый LKG, очистил pending, сохранил отзывы и подтвердил отсутствие отозванных peers в LKG. Это не повторная проверка handshake каждого ранее отозванного клиента. Raw captures и обезличенные результаты хранятся закрыто в `/var/lib/tempest-dns-trial-20261127/`.

Сравнение без временного relay подготовлено только как ограничение: `tpab-g`/`tpab-s` не имеют независимого внешнего uplink, а доступ VM наружу находится в namespace PID 1. Прямой путь потребовал бы новой связности и изменения сетевой топологии; без существенной перестройки и нарушений текущих границ он не запускался. Нестабильность внешнего пути остаётся не локализованной. Внешний WG-клиент и публикация UDP ingress проверяются при первом практическом подключении; VORTEX не изменялся.

## 27.11.2026 · одна сравнительная серия AWG / relay / DoT

Проведено по пять последовательных попыток каждого типа; повторы разных участков не одновременны. Через локальный AWG SOCKS: аутентификация **5/5** (1 мс), HTTPS **5/5** (1164–4753 мс), UDP NTP через SOCKS UDP ASSOCIATE **5/5** (377–584 мс), DoT **5/5** (1384–7343 мс). При единственном штатном apply DoT verifier после своих штатных повторов подтвердил generation 35. Через WG-клиента и полную цепочку: HTTPS **5/5** (967–4186 мс), UDP NTP **4/5** (один timeout 5005 мс), DNS A TCP **5/5** (303–1099 мс), DNS A UDP **5/5** (295–1205 мс), DNSKEY TCP без TC и >512 байт **5/5** (407–2644 мс). Других ошибок/таймаутов в этих отправленных запросах не зафиксировано. Пять первоначальных DNSKEY-вызовов завершились локальной ошибкой выбора режима до отправки запроса; исправлен только диагностический сценарий, затем выполнены пять запланированных запросов.

Relay и оба worker активны, `NRestarts=0`, в журнале за период серии нет записей и ошибок. Relay не публикует счётчики потерь и подавляет часть ошибок IPC, поэтому отсутствие сообщений не доказывает отсутствие потерь. Первая измеренная аномалия — высокая задержка уже при прямом HTTPS/DoT через AWG SOCKS; единственный сетевой timeout серии наблюдался на UDP через WG → TEMPEST → AWG. Разделить relay, внешний AWG upstream, сеть и клиентский участок по последовательным малым выборкам нельзя; вина DNS-адаптера или relay не доказана. Для разделения потребуется сопоставимый тест того же AWG endpoint в разрешённом изолированном namespace без лабораторного relay и с точечным счётом пакетов; не менять host namespace, продуктовый dataplane или сеть VORTEX.

После серии восстановлен предыдущий профиль штатным apply как LKG/active **36**, эквивалентный LKG 29 кроме идентификаторов поколения; pending отсутствует, отзывы сохранены. Профили и критерии verifier не изменялись. Обезличенные результаты и verifier сохранены закрыто в `/var/lib/tempest-dns-trial-20261127/comparison-*.jsonl`, `comparison-relay*.{json,txt}` и `comparison-verifier.txt`; диагностический скрипт хранится в VM, не в продукте. Исходные изменения репозитория сохранены, VORTEX не изменялся.

## 27.11.2026 · AF_NETLINK разрешён владельцем; DoT нестабилен

Владелец разрешил только для `tempest-awg-dns.service` добавить `AF_NETLINK`. Официальный sing-box 1.14.2 с закреплённым SHA запустился с единственным изменением; unit обновлён в VM и репозитории. У работающего процесса проверены UID 992/GID 982, пустые все capability sets, `NoNewPrivs=1`, seccomp и namespace `tpab-g`, отличный от PID 1. Остальные ограничения unit сохранены.

Штатный `/core/apply` подтвердил generation 32 после verifier с TCP/UDP A, HTTPS, DIRECT/BLOCK и DNSKEY по TCP без TC. Однако последующие реальные проверки DNS дали нестабильные результаты: первый полный traffic test — TCP и UDP A fail, повтор — TCP fail и UDP pass; HTTPS, DIRECT/BLOCK, IPv6 и UDP NTP в обоих проходах pass. В соответствии с указанием владельца предыдущий профиль возвращён штатным apply как generation 33, идентичен прежнему LKG 29 за исключением идентификаторов поколения; отзывы сохранены. На generation 33 TCP/UDP DNS и HTTPS прошли, UDP NTP дал отказ, поэтому причина нестабильности транспорта не установлена. Временная отдельная проверка адаптера с текущими SOCKS-учётными данными дала один отказ из трёх TCP A, затем шесть TCP A и DNSKEY прошли; пять прямых DoT-запросов через AWG SOCKS прошли. Временная служба удалена.

Повторный штатный apply DoT получил HTTP 409; Agent автоматически восстановил legacy LKG 33, deployment profile также возвращён, pending отсутствует, все три отзыва сохранены. Реальные DoT fault/leak/recovery испытания после устойчивого подтверждения **NOT_RUN**; не выдавать отдельный успешный verifier за стабильную работу. Следующий шаг — выявить причину периодических отказов DNS/HTTPS и повторить проверки. CI/CodeQL не запускались, VORTEX не изменялся.

Бинарники не добавлены в репозиторий. sing-box распространяется под GPL-3.0-or-later: перед поставкой отдельно проверить обязательства распространения и уведомления зависимостей; пока используется внешний операторский бинарник.

`scripts/lab/dns-adapter-synthetic.py <путь к sing-box>` проверил на loopback TCP и UDP, DNSKEY >512 байт без TC по TCP, SOCKS5 с обязательными учётными данными, числовой IP назначения, SNI, отказ при несовпадении имени и недоверенном сертификате, отказ при остановке SOCKS и имитации недоступного upstream без прямого подключения к работающему тестовому TLS-серверу. Это синтетическое доказательство адаптера, не Xray → AWG и не доказательство всей DNS-политики. Системный DNS, маршруты и firewall не менялись. Закреплённый Xray 26.10.31 и sing-box приняли сгенерированные конфигурации через свои config checks. Targeted Windows pytest: 31 passed, 11 skipped; отдельный test verifier: 1 passed. Linux-only AF_UNIX/SO_PEERCRED и systemd runtime: `NOT_RUN_ON_WINDOWS`. Реальная AWG VM, внешние DNS и CI/CodeQL: `NOT_RUN`.

Для нового поколения AWG оператор **явно** задаёт `awg_dns` в защищённом deployment profile: числовой IPv4 `address`, сертификатное имя `server_name` и необязательный `port` (по умолчанию 853). Никакой DNS-провайдер не выбирается автоматически. Без этого поля сохраняется прежняя UDP-схема с её ограничением; старые LKG и fingerprints должны оставаться читаемыми. Пример для ручной проверки подходящего сервиса: `{"address":"1.1.1.1","server_name":"cloudflare-dns.com","port":853}`; применимость и политика провайдера ещё не подтверждены. В новом поколении Agent валидирует бинарник/config, запускает AWG → DNS → Xray и сохраняет DNS config в fingerprint/LKG; SOCKS credentials находятся в закрытом файле, не в аргументах. Ошибка восстановления закрывает ingress по существующему контракту. Успешный config check или запуск процесса не подтверждает передачу DNS.

## Блокер DNS

Простые запросы клиента TCP/UDP проходят, но Xray переписывает upstream на UDP и большой TCP DNSKEY ответ приходит с TC. Полноценный DNS не подтверждён. Прямой TCP DNS через AWG SOCKS к испытанным resolvers отклонялся; отдельная TLS-проба к DoT через SOCKS однажды прошла. Попытка встроить DNS-over-TLS через Xray DNS outbound и dialerProxy не дала ответов по TCP/UDP; кандидат отклонён, эксперимент удалён, возвращён UDP LKG и предупреждение панели.

Следующий шаг: исследовать DNS/TLS dialer Xray и возможность полноценного TCP DNS через существующую цепочку; при необходимости оценить проверенный DNS-прокси с SOCKS/TLS. Сохранить fail-closed, LKG и не восстанавливать отозванные ключи. Не считать наличие простого ответа доказательством полноценного DNS.
