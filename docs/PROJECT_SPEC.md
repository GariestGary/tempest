## 1. Контекст и цель

### 1.1. Проблема

Нужно одно самохостируемое приложение на обычном Linux-сервере, которое принимает подключения домашних и удалённых устройств и из одной панели задаёт **как, куда и через какой выход** идёт их трафик.

Сейчас эту задачу решает набор настроек, программ и скриптов: VPN-входы, WireGuard/AmneziaWG, sing-box, раздельные SOCKS/VLESS-выходы, таблицы маршрутизации, DNS, проверки доступности. Управление этим по частям неудобно, отказы трудно диагностировать, а замена/добавление провайдера требует ручных изменений в нескольких местах.

### 1.2. Продукт в одном предложении

**TEMPEST** — self-hosted **VPN gateway / egress orchestrator** для Linux с удобной Web-панелью: **клиент → ingress → правила → выбранный egress (DIRECT / VPN / proxy) → интернет**, с безопасным применением настроек, проверками соединений и автоматическим переключением при отказе.

### 1.3. Основные сценарии пользователя

- Подключить Android/iOS/Windows-клиент по WireGuard, AmneziaWG или VLESS и управлять его интернет-маршрутизацией из TEMPEST.
- Назначить по умолчанию DIRECT для российских/доверенных ресурсов и конкретные исходящие подключения для отдельных сайтов/сервисов.
- Иметь несколько конфигураций одного и того же провайдера/страны: например, несколько NL и PL, плюс собственный VPS, не ограничиваясь фиксированными слотами.
- Вручную указать `service.example → US`, если этот сервис доступен только через US, **без автоматического анализа доступности контента**.
- Отслеживать реальную транспортную работоспособность выходов, быстро понимать, почему соединение не работает, переключаться на запасной выход по явной политике.
- Применять конфигурацию без потери доступа к серверу и при сбое возвращаться к последней исправной.
- Управлять VPN-клиентами, разрешениями и их правилами, отзывать конфигурации устройств.
- Разворачивать и обновлять продукт воспроизводимо, без ручного редактирования десятков конфигов.

### 1.4. Целевая платформа

- **Разработка:** TORNADO, Windows 11, Git + Codex. Для Linux-команд допускается WSL2/контейнерная среда; полноценные сетевые тесты выполнять на отдельной Linux VM/тестовом сервере.
- **Будущий продуктив:** VORTEX, Ubuntu Server 26.04 LTS, Docker Compose, существующие Caddy/AdGuard/Nextcloud/другие сервисы. TEMPEST обязан сосуществовать с ними.
- **Первый релиз:** Linux x86_64/amd64. ARM64 — желателен позже после проверки бинарников и тестов.
- **Схема развёртывания:** один репозиторий и единый `docker compose` для непривилегированных сервисов; **если требуется host-level маршрутизация**, минимальный привилегированный `tempest-agent` запускается отдельно как ограниченный systemd service (см. раздел 5). Не скрывать дополнительный шаг установки агента.
- **Сеть:** хост за роутером с публично доступным входящим адресом/портами через NAT/port forwarding; возможен LAN gateway mode. Не предполагать, что TEMPEST является основным роутером или DHCP-сервером.

## 3. Почему PiTun и что от него наследуем

Исходный проект: <https://github.com/DaveBugg/PiTun> (официальная ветка `master`). На дату планирования в нём есть:

- FastAPI и React UI, SQLite/SQLModel/Alembic, Docker Compose;
- Xray-core как основной dataplane, nftables/TPROXY, режим gateway и режим полноценного router;
- outbound-узлы, подписки, Route Explainer, правила по доменам/IP/устройствам, группы устройств;
- health checks, NodeCircle, балансировщики, failover, журнал, тесты;
- HTTP/SOCKS/transparent ingress **в контексте локального проксирования**;
- управление удалёнными VPS и x-ui-панелями, в том числе их inbound/clients;
- резервное восстановление состояния/изменений в отдельных подсистемах.

**Что не принимать без аудита:** что любые входящие протоколы можно поднять на самом TEMPEST; что AWG работает как обычный Xray WireGuard outbound; что любой драйвер PiTun безопасно применяет nftables и sysctl на хосте; что CI-тесты доказывают отсутствие сетевых утечек; что импорт любой VPN-подписки полноценно поддерживает выбранный тип узла.

### 3.1. Обязательное сохранение сильных сторон PiTun

- Не писать заново действующие CRUD, базовую маршрутизацию, React UI, работу SQLite, auth и тестовую инфраструктуру без доказанной необходимости.
- Не выполнять массовую миграцию Python → C# или React → другой фронтенд.
- Вначале оставить Xray основным движком, затем выделить абстракции адаптеров.
- Не выбрасывать upstream-тесты; адаптировать их по мере эволюции.
- Сохранить `upstream` remote и записывать исходный commit SHA, чтобы можно было сравнивать изменения и осмысленно забирать исправления.
- Не копировать в TEMPEST чужие GPL/AGPL-модули без отдельной оценки лицензии. BSD-3-Clause PiTun позволяет форк с соблюдением уведомлений.

### 3.2. Что можно отложить/убрать из PiTun

Для TEMPEST не приоритетны: управление Wi-Fi AP, DHCP, превращение сервера в полноценный физический роутер, массовая установка на VPS по SSH, управление чужими x-ui-панелями, NaiveProxy sidecar как обязательный компонент. **Не удалять всё это в первом изменении:** сначала найти зависимости, затем отключить за feature flag/режимом и лишь после тестов удалять ненужные ветки. Мы должны сократить привилегии, не разрушив стабильно работающее ядро.

## 4. Границы продукта: что входит и не входит

### Входит (конечное целевое состояние)

1. Самохостируемая Web-панель TEMPEST с авторизацией и журналом действий.
2. Ingress: клиентские соединения WireGuard; далее AmneziaWG и VLESS. Выдача профилей, QR/URI, отключение/отзыв клиента, политики для устройств.
3. Egress: DIRECT, WireGuard, AmneziaWG, VLESS/Reality, Hysteria2 и дополнительные протоколы через адаптеры движков после проверки их возможностей.
4. Provider Manager без ограниченного списка стран/провайдеров: ручной импорт, несколько профилей, теги, группы, приоритеты, состояние и история проверок.
5. Policy Engine: правила по устройству/группе, домену/поддомену, CIDR, IP, порту, протоколу, списку; приоритеты, исключения, действия DIRECT/BLOCK/egress group.
6. Явный AUTO внутри разрешённой группы выходов: выбор доступного по health/latency и failover с hysteresis/cooldown.
7. Диагностика «почему этот домен/клиент пойдёт через этот выход»; наблюдаемость DNS/сетевых проб без хранения чувствительных данных без необходимости.
8. Безопасное применение конфигурации: validate → stage → atomic commit → verify → confirm/rollback; без сетевого захвата хоста.
9. Резервные копии, обновления, миграции БД, экспорт/импорт правил и конфигов, безопасный recovery.
10. Один предсказуемый репозиторий, модульная структура и воспроизводимый запуск.

### Не входит (явно исключено)

- Автоматическое определение, в какой стране фактически работает конкретное видео, песня, платный API или сайт с успешным HTTP-ответом.
- Автоматический геоконтентный анализ с логином в чужие аккаунты или обходом CAPTCHA.
- Обязательная встроенная реализация DPI bypass в MVP. Возможность подключить zapret2 — более поздняя опция, только отдельным решением.
- Полноценная замена Keenetic или OpenWrt, управление Wi-Fi/домашним DHCP/основным WAN из Web-панели.
- Продажа VPN-подписок, биллинг, мультиарендность, публичный SaaS.
- Настольные GUI-клиенты под каждую ОС; выдаём совместимые конфигурации для существующих клиентов.
- Доступ к хосту как «удалённая root-консоль» из браузера.
- Необъявленное переключение на DIRECT, если обязательный VPN упал.

## 5. Целевая архитектура и разделение привилегий

```text
              Windows / Android / iOS / LAN devices
                              │
           ┌──────────────────┴──────────────────┐
           │ WG / AWG / VLESS client connections │
           │ or explicit SOCKS/HTTP/LAN gateway  │
           └──────────────────┬──────────────────┘
                              ▼
                   Ingress adapters / engine
                              │ identity, source, ingress
                              ▼
                  TEMPEST Policy Engine
                device + domain + CIDR + port
                    │                │
             manual override      group AUTO
                    └──────┬─────────┘
                           ▼
                 Egress selection / health
        ┌──────────┬───────────┬──────────────┐
        ▼          ▼           ▼              ▼
      DIRECT     WG/AWG       VLESS         Hysteria2
        └──────────┴───────────┴──────────────┘
                           │
                        Internet

      React Web UI ──HTTPS/Caddy──► FastAPI Control Plane
                                      │
                              SQLite / settings / audit
                                      │ authenticated local RPC
                                      ▼
                              tempest-agent (host)
                     bounded operations: nft/ip/tun/wg
                                      │
                            Linux kernel networking
```

### 5.1. Control Plane (по умолчанию без привилегий)

- FastAPI для API/оркестрации и React/TypeScript UI.
- Работает как непривилегированный пользователь в контейнере; **без** `privileged: true`, `network_mode: host`, `pid: host`, `CAP_SYS_ADMIN`, общего host `/etc`, `/proc/sys`, `/var/run/docker.sock`.
- Доступ к базе данных и только собственным конфигам/секретам через ограниченные volume paths.
- Не выполняет произвольные shell-команды, `sudo`, `nsenter` и прямой `nft`/`ip` от имени API.
- Не публикует панель непосредственно в интернет по умолчанию. В production её отдаёт существующий Caddy с отдельной политикой доступа. Порт внутреннего UI конфигурируемый, дефолт не 80/443 (например, `127.0.0.1:8787` только после проверки занятости).

### 5.2. Tempest Agent (минимально необходимые права)

**Ответ на вопрос «нужен ли широкий контроль над хостом?» — нет, широкие полномочия не обязательны.** Но при настройке kernel WireGuard, policy routing, TUN и nftables **нужны ограниченные привилегии в сетевом namespace, который меняем**. В общем случае полностью избавиться от прав на изменение сети хоста нельзя.

Требования:

- Выделенный **host-level systemd service** с Unix-socket (или иной обоснованно безопасный локальный IPC). Только локальные вызовы; Unix socket доступен строго нужному процессу, возможна проверка `SO_PEERCRED`.
- API агента **типизированный и allowlist-only**, например: `validate_plan`, `stage_plan`, `apply_owned_rules`, `restore_snapshot`, `create_owned_tun`, `manage_owned_wg_peer`, `check_engine`, `read_owned_status`. Никакого `exec(command: string)` и произвольных путей к файлам.
- Доступные привилегии выбирать **по экспериментальной проверке**: `CAP_NET_ADMIN` для сетевых изменений; `CAP_NET_RAW`, `CAP_NET_BIND_SERVICE` — только если реально нужны конкретному процессу. Разделить привилегии агента и пользовательских probe/engine сервисов. Не обещать, что все операции возможны без root; если требуется root, ограничить службой, sandboxing и списком операций. Документировать каждую capability и зачем она необходима.
- Agent владеет **только** объектами `tempest_*`: nftables table/chain/set, ip rule fwmark/table, интерфейсами с именами/ID TEMPEST, локальными конфигами. Никогда `nft flush ruleset`, глобальная смена default route или массовое удаление чужих правил.
- При отказе агента Control Plane остаётся доступен для чтения/диагностики. У agent/engine отдельные health checks и журнал.
- Запрещён прямой доступ Web/API к Docker socket. Удалить/изолировать PiTun-операции массового управления Docker и host networking, а не просто убрать флаг `privileged` и надеяться на работоспособность.
- При невозможности на первом этапе сделать безопасный host-agent — временный **proxy-only mode**, не меняющий маршруты хоста. Привилегированное развёртывание откладывается до безопасной реализации.

### 5.3. Data Plane

- Сохранить Xray как исходный основный proxy engine; поверх него сделать стабильный контракт `EgressAdapter` / `IngressAdapter`.
- WG/AWG могут требовать отдельных движков/сервисов (`wireguard-tools`, kernel module, `amneziawg-go` и т. п.). **Не объявлять AWG эквивалентом Xray WireGuard**: параметры обфускации и реализация отличаются.
- Для VLESS/Hysteria2 использовать Xray, если текущая версия и формат поддерживают нужный режим; sing-box — подключать как отдельный адаптер там, где обосновано. Проверять совместимость форматов и бинарников до выбора движка.
- Разделить «провайдер/конфигурация» (хранится в Control Plane), «выход» (engine adapter) и «маршрут» (policy). Правило не должно зависеть от конкретного формата `.conf` или JSON Xray.
- Поддерживать безопасное обновление конфигов без разрушения всех существующих соединений там, где протокол/engine предоставляет runtime API. Если нужен рестарт — UI честно указывает краткий перерыв.

### 5.4. DNS и маршрутизация

- DNS-резолвинг и классификация доменных правил должны быть согласованы. Определить, где происходит DNS lookup/sniffing, как учитываются CNAME, IPv4/IPv6, кеш и TTL. Проверить DoH/Private DNS клиентов: нельзя обещать обнаружение домена, если его не видно шлюзу.
- Воспрепятствовать маршрутизационным петлям: mark/exempt трафик самих движков, собственные контрольные запросы, локальный LAN и доступ к панели.
- IPv6: **никаких неявных утечек**. Либо полноценная поддержка IPv6 в policy/kill-switch, либо явный контролируемый режим отключения/блокировки IPv6 для защищённых потоков; не выключать IPv6 всего хоста без разрешения.
- Маршрутизировать в первую очередь **трафик управляемых ingress-клиентов** и только явно выбранных LAN-устройств, не переписывая маршруты процессов самого VORTEX.
- При совпадении правил результат должен быть детерминирован и отображаться в Route Explainer. Предварительная модель приоритетов: safety/локальные исключения → точные пользовательские правила для устройства/домена → списки/группы → default; окончательную семантику подтвердить ADR + тестами конфликтов.

### 5.5. Безопасное применение

Минимальный контракт:

1. Сформировать декларативный `NetworkPlan` из проверенных настроек.
2. `validate`: синтаксис, коллизии интерфейсов/портов/марок/таблиц, доступность бинарников, наличие rollback snapshot.
3. `stage`: создать кандидат-конфиг и план diff без изменения текущих правил.
4. `apply`: атомарно либо с управляемыми транзакциями применить **только свои** объекты.
5. `verify`: проверить доступность Control Plane/SSH, egress loop prevention, отсутствие неожиданных изменений чужих таблиц, состояние критических клиентов.
6. `confirm`: пользователь/контрольный канал подтверждает; иначе `rollback` с таймаутом, включая восстановление после перезапуска агента/хоста.

Рекомендации должны быть проверены на Linux VM с отрицательными тестами, а не только Python mocks. В случае «все выходы упали» защищённый маршрут остаётся заблокированным (fail-closed), если пользователь явно не разрешил DIRECT в fallback.

## 6. Модель данных и сущности

Ниже **контракт/термины**, а не команда немедленно создать все таблицы. На этапе миграции переиспользовать существующие модели PiTun там, где это безопасно.

| Сущность | Поля / ответственность |
|---|---|
| `Provider` | `id`, `name`, `description`, `enabled`, `tags`, необязательная метка страны/региона; **не фиксированные страны** |
| `Endpoint` | конкретная конфигурация/protocol/engine, привязка к Provider, безопасное хранение секретов, enabled, priority |
| `EgressGroup` | список endpoints/providers; режим `manual`, `fallback`, `auto_best_healthy`; политика при полном отказе |
| `Ingress` | protocol, listener/interface, порт, адреса/подсети, DNS, допустимые clients, lifecycle |
| `ClientDevice` | identity и credential/peer, friendly name, ingress membership, enabled/revoked, политики доступа, даты использования |
| `DeviceGroup` | именованная группа устройств и общая policy |
| `RouteRule` | enabled, order/priority, matchers (source/device + dest domain/CIDR + port/proto), action (DIRECT/BLOCK/egress/group), override flag |
| `HealthSample` | timestamp, endpoint/route ID, probe type, result, latency, failure classification; bounded retention |
| `RoutingDecision` | вычисленный путь, объяснение и источник правила; диагностический объект без обязательного постоянного хранения всего трафика |
| `ApplyTransaction` | candidate fingerprint, diff, snapshot, stage/status, timeout, confirm/rollback reason |
| `AuditEvent` | кем/когда/что изменено, old/new safe summary, результат; без ключей в логах |

### 6.1. Правила конфигурации

- Все сущности имеют стабильные ID; отображаемое имя и страна — метаданные, а не внутренние идентификаторы.
- `Provider` может иметь N конфигов любого типа и N endpoints в одной стране.
- Client и Provider не обязаны иметь одинаковый протокол; engine bridge решает транзит.
- Ручное правило имеет предсказуемый приоритет выше AUTO. AUTO не должен самостоятельно переназначать домен в другую страну, если пользователь закрепил страну/egress.
- Во всех селекторах продумать нормализацию, wildcard, совпадение суффикса домена, IDN, CIDR, конфликтующие правила, приватные сети.
- На каждом ingress в UI видно «по какой политике» и «куда сейчас пойдёт трафик».
- Секреты **никогда** не возвращаются во всех list/get/status API по умолчанию, не попадают в логи, экспорт и диагностические отчёты. Экспорт секретов — отдельная авторизованная операция, зашифрованный backup — предпочтительно.

## 7. Функциональные требования

### FR-01. Web UI и API

- Русский интерфейс как минимум; архитектура для будущей локализации EN.
- Разделы: Dashboard, Clients, Ingress, Providers, Egress Groups, Routing, Diagnostics/Observer, System/Backup, Settings.
- Состояния: configured, enabled, initializing, healthy, degraded, unavailable, disabled, pending-confirmation, error; не путать «процесс запущен» с «трафик работает».
- Журнал изменений, подтверждение рискованных операций, показать diff перед Apply, explain-route до и после.
- UI работает корректно с десктопа и телефона; без обязательного подключения внешних CDN.

### FR-02. Provider/Egress Manager

- Создание/редактирование/отключение/удаление провайдера и произвольного числа endpoints.
- Импорт: `vless://` и ручной ввод VLESS; WG/AWG `.conf`; ссылки на поддерживаемые подписки; остальные форматы по возможностям адаптера. Импорт AmneziaVPN backup (выбор встроенного VLESS) **после исследования формата**, не придумывать универсальный парсер.
- Привязка к стране, но никаких фиксированных NL/PL/US слотов.
- Тест конкретного выхода через него самого, а не TCP connect до IP сервера; показывать результат и дату последней проверки.
- Группы с ручным выбором, порядком fallback и автоматическим выбором самого работоспособного.
- Не удалять старую рабочую конфигурацию при ошибке обновления подписки.

### FR-03. Ingress/Clients

- WireGuard входящий VPN — первый протокол для функционального MVP.
- Добавление клиента с ключами, DNS, AllowedIPs/routes, назначением адресов без конфликтов, конфигом/QR, отзывом и блокировкой доступа.
- Далее AWG и VLESS входы с валидными профилями для распространённых сторонних клиентов; разные ingress могут жить одновременно.
- Внешний доступ, ограничение на доступ к LAN, DNS/IPv6 leak handling, политики по отдельным устройствам.
- **Удаление клиента должно реально отзывать доступ** в работающем dataplane, а не просто скрывать запись из UI.

### FR-04. Routing

- Порядок правил явный, с возможностью перемещения и просмотра результата.
- Match: устройства/группы/ingress, домены/поддомены, CIDR, порт, протокол; расширяемые списки.
- Actions: DIRECT, BLOCK, конкретный endpoint или EgressGroup.
- Возможность «весь трафик этого клиента → через группу», а `example.com → DIRECT` или `another.example → NL` — исключениями.
- Визуальный explain-route и предупреждения о конфликтах/затенённых правилах.
- Не направлять приватные LAN-сети/управление сервером в глобальные egress без явного разрешения.

### FR-05. Health, fallback и AUTO

- Минимум: DNS resolution, TCP connect, TLS handshake и при необходимости запрос на безопасный контрольный URL **через выбранный egress**; UDP-aware проверки для WG/AWG/Hysteria2.
- Проверки работоспособности туннеля должны учитывать реальные данные (не только наличие процесса/handshake) и не приводить к пинг-штормам.
- History sliding window, минимальное число проб, hysteresis, cooldown, recovery/hold-down; защита от флаппинга.
- Разделять отказ провайдера интернета, DNS, туннеля и конечного сайта. Не переключать все выходы из-за локального WAN outage.
- В AUTO: только кандидаты разрешённой EgressGroup; предпочтение корректно работающему выходу, допустимый tie-breaker по latency/приоритету.
- При отсутствии доступных выходов: BLOCK/fail-closed, либо явный пользовательский fallback, включая DIRECT, если отдельно разрешён.
- **Не проводить автоматическую проверку геодоступности содержимого конкретных сервисов**.

### FR-06. Diagnostics/Observer

- Показ статуса engine/inbound/egress, health истории и причин failover.
- Проба пути `client → routing rule → selected egress`, вывод применённых rule IDs и маркировок.
- Ограниченный сбор недавних доменов/ошибок при добровольном включении. Никакого постоянного сбора содержимого трафика/паролей/tokens.
- Диагностический пакет маскирует адреса, приватные ключи, endpoints, аккаунты и токены по умолчанию.
- Можно дать пользователю рекомендацию «проверь этот маршрут» или «используй другой выход», **но изменение правил — вручную** (кроме явно включённого транспортного failover).

### FR-07. Безопасность/операции

- API auth, ограничение сессий, CSRF/Origin для мутаций при cookie-auth, защита от brute-force, audit, валидация всех пользовательских путей/параметров.
- Минимальные права Control Plane, строгие границы Agent; сетевой интерфейс UI не слушает публично без явной настройки.
- Проверка внешних бинарников и версий, целостности скачивания; запрет на shell-инъекции через import/subscriptions.
- Backup/restore с версионированием схемы; rollback даже после reboot; тест восстановления на отдельной машине.
- CI: backend tests, frontend typecheck/lint/tests/build, security/secret scanning, тесты декларативного плана и интеграционные сетевые тесты в VM.

## 8. Приоритетный MVP и критерии готового продукта

### MVP (первый полностью полезный срез)

1. PiTun форкнут, собирается, тесты проходят; непривилегированный Control Plane отделён от Host Agent.
2. Есть хотя бы два независимых **тестовых** исходящих метода: DIRECT и один реально работоспособный VPN/proxy endpoint (VLESS либо WG; затем оба).
3. Можно создать WireGuard ingress и **тестового клиента** с управляемым доступом.
4. Есть рабочие ручные правила для домена/подсети/устройства, и тест `client → TEMPEST → выбранный egress` подтверждает внешний IP/маршрут.
5. Критическая проверка: падение обязательного VPN **не** отправляет защищённый трафик напрямую.
6. Control Plane/SSH/хостовая сеть сохраняют доступность после неверной конфигурации; откат восстанавливает состояние.
7. Публичные 80/443 и существующие сервисы VORTEX не захвачены (на тестовой VM проверить модель сосуществования).

**После MVP** — AWG и VLESS ingress, дополнительные выходы/подписки, зрелый AUTO/Observer, production migration.

### Определение «готового TEMPEST» (Definition of Done конечного продукта)

- Управление клиентами WG/AWG/VLESS; общий интерфейс, профили и отзыв доступа.
- Динамическое количество провайдеров, несколько endpoints/стран, группы и правила.
- Набор проверенных egress: DIRECT, WG, AWG, VLESS, Hysteria2; если протокол не может быть реализован безопасно на платформе, проблема явно задокументирована и не помечена готовой.
- Ручные правила управляют выбором страны/провайдера, AUTO переключает только по транспортному состоянию.
- Сетевая изоляция, fail-closed, без утечек IPv4/IPv6/DNS при отказах, есть наблюдаемость и rollback.
- Документированная установка на совместимый Linux, воспроизводимый backup/restore, CI и отдельный production cutover plan.
- Отсутствие зависимости от старой TEMPEST 2 после **явного** и проверенного переключения.

## 9. Важные нефункциональные ограничения

### 9.1. Совместимость с существующей инфраструктурой

- VORTEX — не выделенный пустой роутер. Есть Caddy, AdGuard Home и уже работающие network services.
- **Не переназначать порты 80/443/53/другие занятые без предварительного preflight и явного одобрения.** Адреса, порты и интерфейсы конфигурируемые.
- **Не менять глобальный resolver** (`/etc/resolv.conf`) по умолчанию; DNS для TEMPEST клиентов должен быть изолирован.
- **Не менять default route хоста**, не удалять чужие nftables/iptables/policy rules, не останавливать существующие VPN/zapret процессы.
- Считать текущую рабочую конфигурацию внешним владельцем сетевых ресурсов до миграции. Нет «автоимпорта с последующей остановкой» без сравнения и проверки.

### 9.2. Ресурсы

- Минимизировать CPU/RAM/disk на сервере с ограниченными ресурсами; фиксировать budgets после бенчмарка на целевом классе хостов.
- Не создавать лишний системный DNS/DHCP/metrics collector без необходимости.
- Ограничить retention логов, метрик, DNS-истории и размер Docker logs.
- Проберы не должны создавать десятки постоянных активных соединений на каждый домен.

### 9.3. Надёжность

- Идемпотентность apply и restore после перезапуска.
- Старые активные соединения не рвать без необходимости, а если разрыв неизбежен — предупреждать в UI.
- Наличие last-known-good и журнала всех network plan changes.
- Конфиг, который не проходит валидацию, не применяем.
- Все важные флаги имеют безопасные значения по умолчанию.

## 11. Архитектурные принципы для исходного кода

1. **Fork-first, not rewrite-first.** Сохранить основу PiTun и тесты, пока обоснование замены не зафиксировано.
2. **One source of truth.** DB/policy модели — источник истины; engine configs генерируются и применяются как производные артефакты.
3. **Least privilege by design.** Нет общего root shell и широкого Docker socket из API.
4. **One network owner.** Агент управляет только объектами TEMPEST. Ownership маркируется/называется и проверяется перед удалением.
5. **Modular adapters.** Protocol/engine/provider отделены от UI и правил.
6. **Manual wins.** Чёткие override приоритеты; автоматизация не переопределяет пользователя.
7. **Fail closed for protected flows.** В отсутствие разрешённых выходов не утекать в DIRECT.
8. **Explainability.** Любой маршрут можно диагностировать до и после применения.
9. **No invented support.** Поддержка протокола «готова» только после конфиг-генерации, реального dial, полного e2e и проверки поведения при отказе.
10. **Safe migration.** Никакой замены продуктивных ресурсов без отдельного тестирования и подтверждения.
11. **Small, reviewable changes.** Каждый этап — небольшие коммиты непосредственно в `master`, с тестами и обратимостью.
12. **Respect licenses.** BSD upstream notices; независимая проверка лицензий зависимостей и возможных заимствований.

## 12. Минимальные интерфейсы будущих адаптеров (эскиз)

> Это эскиз контракта. Имена методов уточнить после аудита PiTun и оформить ADR. Не нужно реализовать всё на нулевом этапе.

```python
from typing import Protocol

class EgressAdapter(Protocol):
    kind: str

    async def validate(self, endpoint: dict) -> list[str]: ...
    async def provision(self, endpoint: dict) -> str: ...
    async def start(self, endpoint_id: str) -> None: ...
    async def stop(self, endpoint_id: str) -> None: ...
    async def probe(self, endpoint_id: str, target: str) -> dict: ...
    async def status(self, endpoint_id: str) -> dict: ...
    async def remove(self, endpoint_id: str) -> None: ...

class IngressAdapter(Protocol):
    kind: str

    async def validate(self, ingress: dict) -> list[str]: ...
    async def apply(self, ingress: dict) -> None: ...
    async def create_client(self, ingress_id: str, client: dict) -> dict: ...
    async def revoke_client(self, client_id: str) -> None: ...
    async def status(self, ingress_id: str) -> dict: ...
```

Секреты и apply транзакции через отдельные сервисы, не через аргументы UI напрямую. Проверка availability/latency не должна изменять основной конфиг. В сквозном e2e проверять **реальный egress**, а не адрес самого VPN-сервера.

## 13. Тестовая стратегия и security-gates

### Автоматические тесты на каждом этапе

- Python: pytest существующих и новых модулей; migrations/backward compatibility.
- Frontend: TypeScript typecheck, ESLint, Vitest/build согласно upstream.
- Статика: format/lint/security, тайны и ключи не попадают в git/logs.
- Контракт: API schemas, state transitions, сериализация, idempotency, invalid inputs.
- Конфиги движков: генерация + запуск `xray -test`/эквивалент для установленной версии в CI/integration.

### Обязательные integration/security тесты

- Есть контрольный доступ к Linux VM по независимому каналу; применить ошибочный `NetworkPlan`, дождаться rollback, проверить возврат.
- Проверить таблицы nftables и `ip rule` до/после: чужие объекты не меняются.
- Убедиться, что API-контейнер не имеет `privileged`, Docker socket, host PID/network и необязательных capabilities.
- Проверить DNS и IPv4/IPv6 утечки при нормальном соединении, падении egress, падении engine и reboot.
- Проверить правильный выходной IP для DIRECT и нескольких VPN-методов.
- Отозвать клиента и убедиться, что существующие/новые авторизации больше не проходят согласно выбранной модели отзыва.
- Проверить route precedence, wildcard, CIDR, конфликтующие правила и петли.
- Нагрузочно проверить разумное число одновременных клиентов и устойчивость к отказу одного endpoint.
- Проверить backup/restore на чистой VM, в том числе ошибки/конфликты.

**Ни один интеграционный тест с root/capabilities не запускать на VORTEX production по умолчанию.** В коммите и отчёте указывать точные команды, результаты и ограничения проверки.

## 14. Управление требованиями и изменениями

При необходимости изменить существенное решение из раздела 2:

1. Завести ADR: проблема → варианты → компромиссы → выбранный вариант → последствия → план миграции.
2. Обновить этот документ в том же изменении на `master`.
3. Не менять принятый scope без обсуждения с пользователем.
4. Если новая функция увеличивает привилегии или может разорвать SSH/сеть — обязательны отдельные тесты отказа и явное подтверждение.

Счётчик фаз и чекбоксы — официальный статус, а не произвольная оценка процентов. Фазу можно отметить выполненной только после всех acceptance gates, включая ручные испытания, если они требуются.

### 16.1. Однократная подготовка GitHub

2. На TORNADO клонировать **свой** форк (не оригинал в директорию с чужим именем). Пример PowerShell:

```powershell
git clone https://github.com/<YOUR_GITHUB_USERNAME>/tempest.git
cd tempest
git remote add upstream https://github.com/DaveBugg/PiTun.git
git fetch upstream --tags
git remote -v
git rev-parse HEAD
```

Заменить `<YOUR_GITHUB_USERNAME>` на реальное имя и уточнить путь/имя репозитория, если GitHub оставил `PiTun`. **Команды не создают fork автоматически** — его нужно предварительно создать в GitHub.

3. Из стартового архива TEMPEST поместить `PROJECT_SPEC.md` в `docs/PROJECT_SPEC.md`, `AGENTS.md` в корень репозитория.
4. Переключиться на `master`, выполнить работу непосредственно в этой ветке и открыть Codex в корне репозитория. Не создавать рабочие ветки или Pull Requests без отдельного запроса пользователя.

### 16.2. Стартовый запрос Codex (копировать целиком)

> Прочитай `AGENTS.md` и `docs/PROJECT_SPEC.md` полностью. Это новый продукт **TEMPEST** на основе форка PiTun. Выполняем **только этап 0**. Сначала проинвентаризируй исходный проект, зафиксируй upstream SHA, архитектуру, карту критичных сетевых/привилегированных операций, gap matrix относительно TEMPEST, baseline тестов и проект ADR-001 по разделению Control Plane / Host Agent. Не меняй рабочие сетевые правила, DNS, роуты, VPN, host Docker settings; не разворачивай PiTun в привилегированном режиме. Не начинай этап 1 и не делай большой рефакторинг. Если есть неясность, которая влияет на безопасность/архитектуру, задай вопрос. В конце представь отчёт: изменённые файлы, выполненные тесты, проблемы, SHA и чекбоксы, которые можно подтвердить. Переход к следующему этапу — только после моего подтверждения.

### 16.3. Чего НЕ делать в первой сессии

- Не запускать `install.sh` из PiTun на рабочем VORTEX.
- Не запускать upstream production `docker-compose.yml` на VORTEX: он содержит опасные настройки полномочий и слушает 80/443.
- Не запускать команды `nft`, `iptables`, `ip route`/`ip rule`, `sysctl` с изменением состояния на рабочем хосте.
- Не удалять код PiTun массово, даже если кажется, что он не нужен.
- Не переписывать backend на .NET; не добавлять zapret2, сервисное геообнаружение и функции вне текущей фазы.
