# Working Core на тестовом стенде

Профиль объединяет авторизацию и Web UI PiTun, SQLite и отдельный Xray Agent. Xray 26.10.31 завершает WireGuard в userspace. Панель хранит черновик, Agent хранит активное поколение, подтверждённый LKG и список отзывов. Текущий статус живых испытаний приведён в [STATUS](STATUS.md).

## Состояние прогона 2026-11-26

Реальный пользовательский профиль из UI прошёл WG handshake, TCP/UDP и DNS через TLS; отдельно подтверждён Reality/Vision через WG. Отказы upstream, невалидные UUID/Reality, LKG, restart, reboot и отзыв проверены с ограничениями в [матрице STATUS](STATUS.md#2026-11-26--working-core-live-проверка-к-ревью). Отдельно проверены отзыв уже открытых потоков и пример Linux client kill-switch; внешняя клиентская VM и публикация UDP ingress остаются непроверенными: [результаты](STATUS.md#2026-11-26--a-отзыв-активных-потоков-и-клиентский-kill-switch).

Панель слушает VM localhost:8787; на TYPHOON используйте `ssh -N -L 127.0.0.1:8787:127.0.0.1:8787 lab`. Учётная запись `admin`; bootstrap-пароль хранится только в `/var/lib/tempest-core-private/bootstrap-password` внутри VM. Приватные ключи, профили, синтетические upstream-конфиги и сырые captures находятся в закрытом `/var/lib/tempest-live-acceptance-20261126` и не входят в Git.

На проверенной VM boot ordering установлен [сценарием](../scripts/lab/working-core-boot-install.sh): topology → sink/upstream/probe → Agent/LKG → Compose, отдельный userspace user peer. Он использует защищённые копии скриптов в `/opt/tempest/bin`, включённые `tempest-lab-*` units и запускается при reboot. Сценарии в `scripts/lab/working-core-*` фиксируют точные имена и UUID VM и отказывают при коллизиях; перед созданием нового стенда сверить UUID, selectors, исходный SHA, свободные пути, recovery и консоль. Bootstrap Agent использует `TEMPEST_LAB_EXPECTED_SHA` для явно проверенного полного SHA checkout. Первичное создание требует operator provisioning fixture, зависимостей и отдельно созданного UI-профиля; boot-сценарий не является универсальным installer.

Штатный Ubuntu-профиль `wg` разрешает тестовые ключи из `/etc/wireguard`; для двух userspace sockets в конкретной VM потребовался согласованный local override. Исходный профиль не менялся, enforcement сохранён. После остановки использующих сокеты lab clients откатить только неизменённый override можно командой `sudo bash /home/gary/working-core-wg-apparmor.sh --rollback`: скрипт сверяет сохранённый исходный профиль и точное содержимое override перед удалением. Agent, Xray и Control Plane дополнительных прав не получили.

Docker внутри VM создаёт собственные bridge/NAT/firewall объекты; их снимки сохранены отдельно от product namespace. Включённый контейнерный профиль и лабораторные systemd units оставлены работающими для ручной проверки. Не восстанавливайте старый QCOW2 поверх текущего журнала без отдельной сверки уже выполненных отзывов.

Для повторения тестов активных потоков и клиентского фильтра предназначены `scripts/lab/working-core-active-revoke.py` и `scripts/lab/working-core-killswitch.py`. Первый отзывает строго именованный тестовый профиль и требует заранее включённый профиль этого клиента; второй временно создаёт veth и отдельную nft table только в тестовых namespaces. Перед повтором проверить идентичности namespaces, свободные селекторы, независимую консоль и перенести или сохранить прежние captures; команды требуют root в согласованной VM. Фильтр является демонстрационной политикой конкретного клиента, а не частью установленного TEMPEST.

## Подготовка согласованной VM

Используйте disposable Ubuntu amd64 с независимой консолью и проверенной копией для восстановления. Сверьте checkout `master`, origin, проверяемый SHA, сетевые пространства и отсутствие коллизий. Для испытаний нужны отдельные namespace gateway и контрольного WireGuard peer, тестовый VLESS TCP/TLS upstream и контролируемые TCP/UDP/DNS назначения. Ниже используется исходная топология A/B. [Топология с точными адресами и интерфейсами](ENGINE_VS_KERNEL_DECISION.md)

1. Подготовьте Xray по [systemd-шаблонам](../deploy/systemd/README.md) и [контракту lifecycle](XRAY_MVP_LIFECYCLE.md). Проверьте SHA-256 бинарника `cc4b84d3069569f297a61f04b914f2bb37e9d202fd7b84cb50def1fc30fd40e1` и разделение UID/GID. `tempest-xray-agent.service` запускается после появления namespace и runtime-каталога. Для исходного стенда в копиях unit укажите `tpab-g` и `tpab-c` вместо шаблонных имён. Agent запускает и останавливает Xray сам. Probe unit должен использовать заранее подготовленный туннель контрольного peer и доверенный verifier. Для A/B пригоден [существующий verifier](../scripts/lab/xray-mvp-probe.py).
2. В закрытом provisioning-каталоге создайте `deployment.json` по примеру ниже. Закрепите два разных WG ключа. Закрытый ключ gateway используется в `private_key`. Публичный ключ отдельного probe-клиента используется в `probe.peer.public_key`. Закрытый ключ probe остаётся на probe-клиенте. Укажите фактически опубликованный **числовой** endpoint для клиентского конфига. DNS и probe rules должны совпадать с доверенным verifier. Для другого upstream подготовьте контролируемый sink и ожидаемые адреса источника при VLESS и DIRECT.
3. В том же каталоге положите случайный `app-secret` (минимум 32 байта) и `bootstrap-password` (случайная строка 16–72 байта). Каталог и файлы должны быть закрыты для прочих пользователей и доступны на чтение UID контейнера API, по умолчанию 10001. Проверьте фактический UID/GID с учётом Docker user namespace. Разрешите этот UID и числовой GID `tempest-control` в environment Agent. API читает только provisioning и Unix socket. Сохраняйте `app-secret` вместе с защищённой копией SQLite, от него зависит расшифрование VLESS.
4. Запустите согласованный Agent и убедитесь, что `/run/tempest-xray-agent/control.sock` принадлежит нужной группе. Для первого запуска панели используйте отдельный журнал. Миграция профилей из журнала CLI требует отдельного сопоставления peer с БД панели, иначе исключённые из нового поколения ключи считаются отозванными. Compose монтирует каталог сокета, чтобы API переподключался после замены файла при рестарте Agent.

Пример формы `deployment.json` для адресов A/B. Ключи в примере требуется заменить перед стартом.

```json
{
  "target_namespace_id": "tpab-g",
  "listen_address": "192.0.2.1",
  "listen_port": 51871,
  "client_endpoint_address": "192.0.2.1",
  "client_endpoint_port": 51871,
  "tunnel_addresses": ["10.88.0.1/32", "fd42:88::1/128"],
  "client_pools": ["10.88.0.0/24", "fd42:88::/64"],
  "private_key": "<GATEWAY_WG_PRIVATE_KEY>",
  "resolvers": ["198.51.100.53", "2001:db8:2::53"],
  "probe": {
    "peer": {
      "public_key": "<PROBE_WG_PUBLIC_KEY>",
      "addresses": ["10.88.0.2/32", "fd42:88::2/128"]
    },
    "rules": [
      {"destination": "198.51.100.10/32", "port": 18080, "egress": "direct"},
      {"destination": "198.51.100.20/32", "port": 18080, "egress": "vpn"},
      {"destination": "198.51.100.30/32", "port": 18080, "egress": "block"},
      {"destination": "2001:db8:2::10/128", "port": 18080, "egress": "direct"},

```

## Запуск панели

В разделе «Сохранённые выходы VLESS» можно сохранить до 64 именованных ссылок VLESS TCP/TLS и выбрать одну для черновика. Выбор не меняет работающий Xray до просмотра и применения изменений. Все правила `VLESS` и DNS используют один выбранный выход; назначение разных выходов отдельным правилам ещё не реализовано. Секреты сохраняются зашифрованными в SQLite и не возвращаются списком. При ручной замене единственного выхода выбор сохранённой записи снимается. Для удаления выбранной записи сначала выберите другую или вручную замените выход.

Команды рассчитаны на согласованный стенд с Docker Compose и свободным локальным портом. Compose создаёт собственную bridge-сеть для Web/API. Изменения сети WireGuard, маршрутов и адресов выполняются оператором только в согласованных test namespaces. Приложение работает с одним Uvicorn worker на отдельном SQLite volume.

```bash
export TEMPEST_AGENT_GID="$(getent group tempest-control | cut -d: -f3)"
export TEMPEST_CORE_PRIVATE_DIR=/path/to/private-working-core
export TEMPEST_PANEL_PORT=8787
docker compose -f docker-compose.working-core.yml config --quiet
docker compose -f docker-compose.working-core.yml up --build -d
```

Откройте `http://127.0.0.1:8787` на VM или через разрешённый SSH forwarding. Войдите как `admin` с bootstrap-паролем. Пароль используется только при создании первой учётной записи.

1. Введите адрес, порт, UUID и TLS-имя VLESS либо импортируйте `vless://`. Для домена укажите dial IP, сохранив TLS-имя из ссылки. Для частного сертификата задайте согласованный SHA-256 pin. Поддерживается VLESS TCP/TLS без дополнительных transport/flow режимов.
2. Создайте WireGuard-клиента и сохраните загруженный `.conf` в закрытом месте. Клиентский ключ выдаётся один раз. Если файл потерян, отзовите профиль и выпустите новый.
3. Добавьте правила CIDR + порт для TCP/UDP. Для A/B добавьте собственные правила к `.10`/ `::10`, `.20`/ `::20` и `.30`/ `::30` из примера с соответствующими действиями. Правила probe действуют только для его адресов. Все остальные назначения без пользовательского разрешения блокируются. Разрешённые DNS-серверы получают TCP/UDP на 53 через VLESS. Другой DNS на 53/853 блокируется. DoH на 443 следует обычным правилам.
4. Нажмите «Посмотреть изменения», затем «Применить конфигурацию». Панель подготавливает и применяет кандидат через IPC. Agent подтверждает его после проб в том же поколении. При сбое сохраняется безопасный LKG. Восстановление LKG доступно после восстановления upstream, если ingress остался закрыт после ошибки. Применение требует краткого переподключения WireGuard.
5. Откройте профиль на отдельном WireGuard-клиенте. Проверьте маршрут к endpoint вне туннеля и включите поддерживаемый клиентом kill-switch/always-on. Сервер контролирует трафик, доставленный в туннель. Поведение при отключении туннеля определяется ОС клиента.
6. Нажмите «Отозвать» рядом с клиентом. Agent фиксирует отзыв до повторного запуска текущей политики. При невозможности безопасно восстановить оставшийся ingress он остаётся закрыт. Возврат LKG и рестарт Agent сохраняют отзыв.

## Сценарий приёмки

- На новой БД войдите через браузер, импортируйте VLESS, создайте профиль, задайте правила и подтвердите изменения через UI. Смотрите generation и результаты probe в Agent. Проверьте штатный ручной ввод VLESS отдельно.
- Для реального пользовательского профиля используйте отдельный клиент `tpab-w`, чтобы пробер в `tpab-c` оставался доступен. Для предполагаемого испытания согласуйте линк `tpab-gw` ↔ `tpab-wc`, адреса `192.0.2.5/30` ↔ `192.0.2.6/30`, маршрут к `192.0.2.1/32` через `192.0.2.5` и новый WG интерфейс `tpab-user` в `tpab-w`. Используйте выданные панелью ключ, адреса и маршруты. Probe по-прежнему использует `tpab-wg` в `tpab-c`.
- С пользовательского peer прогоните TCP и UDP для IPv4/IPv6 по DIRECT, VLESS и BLOCK. Сверьте маркеры и адрес источника на sink. Проверьте A/AAAA по TCP и UDP и отказ для других DNS/DoT путей. Смените пользовательское DIRECT правило на VLESS и подтвердите новый наблюдаемый источник, сохранив независимые пробы Agent.
- Остановите согласованный тестовый VLESS upstream и подтвердите BLOCK для защищённых путей с положительным прямым контролем. Проверьте отказ Apply с неверным UUID, возврат к LKG при исправном upstream, рестарт Agent, reboot после согласованного boot provisioning и целостность отзыва. У отозванного профиля не должно быть новой успешной авторизации или передачи данных после Apply, восстановления и reboot.
- Сверьте UID/GID, capability masks, `NoNewPrivs`, socket/FS/namespace boundaries, отсутствие TUN у gateway и Docker socket у Web/API, состояние сети PID 1 и независимый канал до и после. Удаляйте только согласованные временные объекты стенда. SQL volume и журнал LKG сохраняются при штатной остановке.

Для остановки панели используйте `docker compose -f docker-compose.working-core.yml down`. Остановка UI/API сохраняет текущую работу Xray и данные. Agent и тестовую топологию останавливает оператор в согласованных границах.
