# ADR-001 — граница Control Plane и Network Agent

Дата 2026-11-10. **Предложено на этапе 0.** Окончательная приёмка архитектуры зависит от Linux VM и Gate 2. Связано с D-006, §5 и §9 [спецификации](../PROJECT_SPEC.md).

## Контекст

Production PiTun соединяет HTTP, DB, Xray, host PID/network, Docker socket, nftables/ip и общесистемный DNS в одной доверенной зоне. Привязка к имени таблицы `pitun` не ограничивает Linux capabilities процесса. MVP TEMPEST принимает трафик своих VPN-клиентов, может управлять выделенным интерфейсом и должен оставаться доступным при отказе egress или ошибочном apply. Для доступа к физическому LAN может понадобиться ограниченная работа в host namespace. [Карта доступа к хосту](../HOST_PRIVILEGE_AUDIT.md).

## Варианты

| Вариант | Что даёт | Цена и граница риска |
|---|---|---|
| A. Отдельный host agent под systemd | Прямой доступ к kernel WG, nftables и policy routing хоста. Удобен для явно включённого LAN gateway; близок к исходному dataplane. Установка агента отдельным шагом. | Даже ограниченный unit с `CAP_NET_ADMIN` в host netns способен менять всю сеть этого namespace при компрометации. Ownership и allowlist проверяет код. Возможны коллизии fwmark/table/ports, разрыв SSH и конфликт с Compose/firewall других владельцев. |
| B. Изолированный dataplane и агент в отдельном netns | Kernel WG/TUN/forwarding/policy в выделенном namespace. У API остаётся обычная bridge-сеть. Можно разместить агент отдельным systemd unit или sidecar с network capability только в своём namespace и без host PID/Docker socket. | Нужны явные ingress UDP, veth/bridge или port publication, NAT/MTU/IPv6 и управление lifetime. Docker port publication сам может создать host firewall/NAT-правила. Хостовые операции по подключению namespace выполняет оператор или отдельный узкий компонент. Прозрачный LAN захват потребует дополнительной схемы. |
| C. Явный proxy-only | Обычные TCP/UDP listeners и локальный dataplane; API и движок разделены. Подходит для безопасной разработки и проверки DIRECT/VLESS на TCP без управления хостовой сетью. | Нет kernel WG ingress, прозрачного LAN forwarding и соответствующих гарантий gateway. |

Оставить production PiTun с отключённым только флагом `privileged` или перенаправить Docker API через имеющийся proxy недостаточно: остаются host PID/network, socket, системные mounts и достижимые пути широких мутаций.

## Предложение

Выделить непривилегированный Control Plane и установить `tempest-agent` отдельно только там, где нужны сетевые права. Для управляемого VPN ingress первым проверять вариант B с dataplane в выделенном netns. Systemd может запускать Agent в заранее созданном namespace через `NetworkNamespacePath=`; открывать host namespace из API или агента через `nsenter` не требуется. Вариант A оставить для явно настроенного режима, которому действительно нужен доступ к host netns. Если B не удовлетворяет требованиям проверки, зафиксировать точную причину и вернуться к выбору перед принятием ADR. Вариант C доступен без host-агента до подтверждения сетевого режима.

Явно решить, где создан kernel WG-интерфейс: его зашифрованный UDP socket остаётся в namespace создания даже после переноса интерфейса. Операторский preflight включает публикацию порта, пересечения подсетей, DNS, MTU, IPv6, доступный путь возврата и валидацию существующего firewall. Модель сосуществования проверяется на VM с аналогами Caddy/AdGuard/SSH. [WireGuard netns](https://www.wireguard.com/netns/), [systemd.exec](https://github.com/systemd/systemd/blob/main/man/systemd.exec.xml).

## Полномочия и граница IPC

- Control Plane хранит желаемое состояние, собирает план и проводит пользовательскую авторизацию. FastAPI, React, SQLite и чистые генераторы PiTun остаются основой. Непривилегированный UID, отдельные volumes, без host PID/network, host Docker socket, системных mounts и capabilities. Управление и dataplane имеют отдельные identity и lifecycle.
- Агент принимает типизированные запросы через локальный Unix socket с ограниченными правами, проверкой peer credentials и маппинга UID контейнера, если он включён. Один авторизованный вызывающий процесс, лимиты размера/частоты запросов и таймауты. Минимальный набор операций — `validate`, `stage`, `apply`, `read_status`, `confirm`, `rollback`. Идентификатор операции и актор из Control Plane используются для корреляции в журнале. Аутентификация процесса дополняет проверку самого плана на стороне агента.
- Вход агента — версии плана, конкретные операции и принадлежащие ресурсы. Произвольные shell, nft text, пути, env и параметры systemctl/SSH отсутствуют в контракте. Агент независимо валидирует namespace, принадлежность интерфейсов/peer, CIDR, порт, mark/mask, table и priority. Параллельные apply сериализуются, а повторное применение использует generation/fingerprint. При коллизии с чужим объектом запрос отклоняется. Реестр владельца хранится на диске отдельно от UI.
- `CAP_NET_ADMIN` — кандидат для nftables, маршрутов, link/addr и kernel WG в целевом namespace. TUN требует доступа к `/dev/net/tun` при его фактическом использовании, с проверкой владельца и прав на создание/открытие устройства. `CAP_NET_RAW` рассматривать только для подтверждённых raw/mark операций отдельного процесса; проверить `SO_MARK` и `IP_TRANSPARENT` на целевом ядре. `CAP_NET_BIND_SERVICE` обсуждать только при необходимости низкого порта с учётом настройки namespace. Ни один из этих доступов не назначается API. Runtime не загружает модули ядра и не требует `CAP_SYS_ADMIN`; готовность ядра и создание namespace — preflight и setup оператора. [Linux capabilities](https://man7.org/linux/man-pages/man7/capabilities.7.html).
- Кандидаты для unit hardening — отдельный UID, `NoNewPrivileges`, минимальные `CapabilityBoundingSet`/`AmbientCapabilities`, `ProtectSystem`, `ProtectHome`, ограничение адресных семейств, устройств и путей записи. Проверить совместимость с netlink, IPC и TUN. Журналы агента и резервные снимки защищаются от записи из API, вывод маскирует ключи. Engine не наследует полномочия агента.

## Apply и восстановление

1. Агент принимает план с идентификатором поколения и проверяет ownership и коллизии. Сохраняет diff кандидата и полный last-known-good для собственных объектов. Stage не меняет активное состояние.
2. Перед изменениями записывает durable pending transaction и deadline. Сначала обеспечивает защиту управляемого трафика от неявного DIRECT, затем применяет nft batch и упорядоченные операции ip/WG/engine. Один nft batch атомарен внутри nftables. Остальные подсистемы используют компенсирующие операции и явные проверки результатов.
3. Verify проверяет принадлежащие объекты, связность egress, отсутствие DNS/IPv4/IPv6 обхода и доступ по независимому каналу. Подтверждение привязано к поколению. При ошибке, таймауте, потере IPC или reboot до подтверждения агент восстанавливает last-known-good либо удерживает управляемый трафик заблокированным при неудачном восстановлении.
4. UI/API остаются доступны для чтения и показывают причину degraded/pending. Reconcile проверяет чужие объекты и не удаляет их. Глобальный default route, системный resolver, firewall других служб, физические интерфейсы и DHCP вне контракта.

## Что подтвердить перед принятием

- Снять возможности реальных процессов через `/proc/*/status`, проверить отсутствие доступа к чужим namespace/объектам, Docker API и системным файлам. Сравнить nft/ip/sysctl снимки и доступность контрольного канала до/после.
- Проверить namespaced WG ingress и отдельный egress через внешний IP, TCP/UDP и DNS, IPv4/IPv6 и отзыв peer. Отдельно измерить, нужна ли host-side маршрутизация для LAN mode, и сравнить kernel WG с возможностями закреплённого Xray. Проверить TUN JSON и какие настройки движка меняют namespace.
- Провести fault injection на VM: коллизии, invalid config, ошибка nft/ip после частичного apply, drop Agent/IPC/engine, reboot до confirm, отказ egress и отказ rollback. Проверить автоматический возврат, ручной recovery и независимый SSH.

Если проверки выявят необходимость дополнительных host-привилегий, сначала описать фактическую операцию, альтернативу и остаточный риск. Этап 0 фиксирует это предложение без изменений реализации.
