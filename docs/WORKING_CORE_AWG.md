# AWG egress: текущая интеграция

Статус: **проверяется в disposable VM; к развёртыванию на VORTEX не готово**. Выбор AWG, конфигурация Xray SOCKS и общий lifecycle Xray/AWG добавлены в незакоммиченное состояние. Реальный WG-клиент в lab прошёл HTTPS, UDP NTP, DNS TCP/UDP, IPv6 BLOCK и проверку внешнего IPv4; проверки отказа и восстановления описаны в статусе. Для доступа к подписке стенд использует временный UDP-релей; отмечались отдельные таймауты контрольных запросов.

Для адаптера рассмотрен [awgproxy](https://github.com/mishamosher/awgproxy) commit `c87c35e40eddac260941ab02596e53d5eb601eae` (ISC), который использует [официальный amneziawg-go](https://github.com/amnezia-vpn/amneziawg-go) `v3.1.20260828`. В режиме без `TunnelDomains` и `LogDomains` его SOCKS использует netstack dial как для TCP, так и для UDP; для UDP поведение зависит от `github.com/things-go/go-socks5` `v0.1.3`. Не включать split-routing: в этом режиме другой callback, а UDP обработчик библиотеки при отсутствии обычного dial может использовать `net.Dial` вне туннеля.

Локально собран кандидат из этого commit с Go `1.27.3` (официальный linux-amd64 архив SHA-256 `65efbc80fdc1fa2cd2631cad5b481777a68e8725f34e89f50fc6ac714e379b40`). Runtime принимает предоставленный профиль, включая параметры AWG 3.x. Исходный конфиг может содержать секреты и не должен попадать в аргументы процессов, логи, Git или отчёты; ошибки парсинга upstream могут содержать значения ключей, поэтому вывод runtime нельзя направлять в обычные логи без безопасного подавления или фильтрации.

Воспроизводимая linux/amd64 сборка выполняется `bash scripts/build-awgproxy.sh <чистый-checkout> <абсолютный-путь-выхода>` с Go 1.27.3 и заранее заполненным проверенным Go module cache. Скрипт фиксирует commit, применяет [небольшой патч bind](../scripts/awgproxy-no-route-monitor.patch), запрещает загрузку зависимостей при сборке и сверяет SHA-256 `e0fe256ad362221026a15a372a246b21026b0405e4dc32ab8f2c87c92543686e`; тот же digest проверяет Agent перед использованием защищённого оператором бинарника `/opt/tempest/bin/awgproxy`. Патч отключает только необязательный netlink-монитор изменений маршрута: протокол, криптография и сетевой bind остаются upstream. Автоматическая реакция на изменение маршрута хоста пока не проверена. Исходный awgproxy — ISC, amneziawg-go и go-socks5 — MIT, gVisor — Apache-2.0. При поставке необходимо приложить уведомления и завершить аудит всех транзитивных зависимостей.

`app.core.awg_bridge` готовит локальный SOCKS профиль из ограниченного набора полей, отвергает неизвестные поля и hooks и не переносит пользовательские секции proxy. Пока принимаются только IP endpoint и числовые DNS с IPv4: это исключает системный DNS fallback; поддержка доменного endpoint требует безопасного явного разрешения адреса. Файл на выходе содержит секреты и предназначен только для защищённого runtime. Определение IPv6 требует одновременно IPv6-адреса интерфейса и IPv6 default AllowedIPs; без них защищённый IPv6 блокируется до VPN. В предоставленном профиле адрес интерфейса только IPv4, несмотря на наличие IPv6 в AllowedIPs. Клиентские DNS TCP и UDP идут к IPv4 resolver профиля через AWG по UDP: TCP/53 в этом испытании отклонялся upstream; большие обрезанные DNS-ответы могут быть недоступны.

26 ноября 2026 в существующей disposable VM после разрешения владельца временный непривилегированный UDP-релей связал `tpab-g` с endpoint подписки через Unix-сокет, без изменения сетевых интерфейсов, маршрутов, DNS или firewall. Через локальный SOCKS AWG runtime прошли HTTPS и UDP DNS; сервис проверки адреса вернул глобальный IPv4. После остановки релея HTTPS через мост не завершился. Процессы и временные копии конфига удалены. Это не доказывает поведение Xray, WireGuard ingress, rollback или отсутствие утечек полной цепочки.

Для завершения необходимо подтвердить общий lifecycle и LKG на живом стенде, обеспечить реальные пробы WG/TCP/UDP/DNS и проверку отказа всей цепочки. Нельзя подтверждать AWG generation только по работающему процессу или валидной конфигурации. Испытание полной цепочки требует контролируемого доступа namespace к подписке; согласованный временный релей допустим только для данного теста. Серверная защита относится только к трафику, дошедшему до ingress; клиентский kill-switch зависит от ОС клиента.

## Подготовка следующего лабораторного испытания

На `tempest-lab-ubuntu` уже работают `tempest-xray-agent.service`, `tempest-xray.service` и лабораторный VLESS verifier. Проверка AWG потребует отдельного согласования точечных изменений этой VM: сохранить копии затрагиваемых файлов и LKG, установить проверенный awgproxy в `/opt/tempest/bin/awgproxy`, добавить отдельную учётную запись `tempest-awgproxy`, unit `/etc/systemd/system/tempest-awgproxy.service` и ограниченное разрешение на его start/stop в `/etc/polkit-1/rules.d/49-tempest-xray.rules`, обновить только используемые файлы Agent в `/opt/tempest/backend/app/` и сборку `tempest-lab-panel.service`, подготовить AWG-aware verifier вместо существующей VLESS-only пробы, затем перезапустить только указанные TEMPEST lab services. Существующий namespace gateway — `tpab-g`, probe — `tpab-c`; PID 1 namespace не менять. До выполнения требуется отдельно проверить актуальную точку восстановления, состояние каждого файла, точную команду сборки панели и селекторы временного UDP-релея; обеспечить чистое восстановление сохранённых файлов, журнала и конфигурации. Реальный `.conf` должен быть предоставлен защищённым путём или импортирован владельцем через панель, а не помещён в Git или отчёт. План не является разрешением на выполнение и не подтверждает наличие готового AWG verifier.
