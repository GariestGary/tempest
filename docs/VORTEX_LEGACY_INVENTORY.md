## Сеть и firewall

В доступных `ip -4/-6 rule` — стандартные таблицы, отдельных правил по именам WG/TUN нет; интерфейсов с очевидными WG/TUN именами не обнаружено. Это не доказывает отсутствие пользовательских dataplane маршрутов внутри контейнеров и скрытых зависимостей. По sudo-отчёту IPv4 `filter/FORWARD` имеет policy `drop`; есть Docker NAT/filter/raw и отдельные цепочки `inet zapret2`. Найдены кандидатные Docker rules по port 9080 (handles 370, 481, 475 и 732 на момент снимка). Нельзя считать все эти правила принадлежащими панели: порт встречается также внутри других контейнеров, handles меняются. UDP 51820 явно не найден как литерал в rules, однако общие правила и цепочки ещё требуют чтения. Не удалять правила вручную по портам/старым handles.

## Исторический план миграции dataplane и старой панели

Этот план создан до решения владельца 2026-11-28 и не является актуальным ограничением на read-only аудит или разрешённое обслуживание TEMPEST control plane. Все пункты, затрагивающие старый контейнер, sing-box/WG ingress, Caddy, guard, другие службы или сетевые объекты, требуют отдельного разрешения и не входят автоматически в обновление control plane.

1. Снять закрытый архив состояния старой панели и относящихся конфигураций: Docker inspect и Compose файлы/override, SQLite/volume, пути и права, текущие unit/drop-ins, `sing-box` конфигурацию и Caddy site. Архив и manifest с контрольными суммами хранить вне Git с ограниченным доступом; состояние секретов и точку восстановления проверить. Сырые `docker inspect` и конфиги могут содержать секреты и не должны попадать в обычные логи.
2. После подтверждения зависимостей зафиксировать и отключить старый guard; `docker update --restart=no vortex-panel` и `docker stop vortex-panel` допустимы только после утверждения и успешного архива. Обратные операции — `docker update --restart=unless-stopped vortex-panel` и `docker start vortex-panel`; volume и контейнер сохранить. Это освободит 127.0.0.1:9080 без изменения общего Caddy.
3. Для потенциального освобождения UDP 51820 сохранить текущий SHA-256 `/etc/sing-box/config.json` и создать **новый закрытый черновик**, не перезаписывая источник, с помощью [`preview-retire-old-wg.py`](../scripts/deploy/preview-retire-old-wg.py). Он удаляет только ровно один ожидаемый endpoint и его inbound reference, отказывает при другом порте, инверсии, неучтённых ссылках или изменённом SHA. До применения требуется приватное сравнение diff, подтверждение отсутствия других потребителей, проверка всей директории `sing-box check -D ... -C ...`, согласованный reload и проверка остальных входов/rules. Изменять system sing-box или Caddy до такого согласования нельзя; старый конфиг и его секреты в Git не переносить.
4. Подготовить и проверить отдельные собственные файлы/службы нового экземпляра, ingress и verifier по [плану развёртывания](FIRST_VORTEX_DEPLOYMENT.md). Только после функциональной проверки нового UI, клиента и сохранности общих сервисов принимать отдельное решение об окончательном удалении старых данных. До этого rollback возвращает старую панель и согласованный старый ingress из проверенного архива с учётом отозванных ключей; восстановление старого конфига не должно без проверки снова активировать отозванных клиентов.
