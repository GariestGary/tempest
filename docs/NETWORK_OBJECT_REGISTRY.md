## Model and invariants

Each `NetworkObject` has a stable ID, typed kind, prepared namespace ID, owner, generation UUID/number, canonical configuration fingerprint, and typed `ResourceClaim` keys. Kinds cover nftables table/chain/rule, `ip rule`, routing table, route, WireGuard/TUN/managed interface. Exclusive claims distinguish nft table/chain/rule selectors, `ip rule` priority, routing table ID, fwmark, route slot and interface name/ifindex; rule mask and match selectors are nonexclusive metadata. A collision is checked across every observed object in the same namespace, including foreign objects and objects with a `tempest-` prefix. Numeric claims use canonical decimal values; priority and fwmark may be zero, while table ID, mask and ifindex must be positive. The Linux adapter constructs canonical keys from parsed kernel objects, including nft family/table/chain and route table/destination/metric; it does not accept an arbitrary encoded key from a caller as an observation.

The registry keeps desired objects separate from independently observed, confirmed receipts. `diff` is read-only and reports added/changed/removed stable IDs. A repeated identical generation is idempotent; reuse with different intent or a stale base generation is rejected. `reconcile_mock` is explicitly test-only: it atomically changes an in-memory inventory after a complete snapshot and CAS revision check. The mock issues random proofs for created objects. Prior to every replacement or removal it rechecks that the live object exactly matches the Agent-held receipt: stable ID, type, namespace, claims, fingerprint and proof. Missing evidence, unexpected drift, incomplete inventory, duplicate ID/claim, or competing generation fails closed. Foreign objects remain untouched; there is no flush or bulk delete command.

The mock proof demonstrates the control flow, not Linux ownership. A production implementation cannot infer ownership from a name, tag, fwmark, content hash, or a user-supplied owner field. It needs an Agent-protected creation journal plus fresh kernel observations tied to a stable, non-reused identity. If a subsystem cannot provide enough evidence after restart or handle reuse, the Agent must report a conflict and leave the object untouched. The namespace identity must be checked against the prepared target, not merely its display name.

## Read-only Linux collection boundary

`backend/app/network_agent/linux_inventory_capture.py` is an operator-run module for a separate disposable Linux VM. Its six command argv are fixed in code: link; IPv4 and IPv6 rules; IPv4 and IPv6 routes across all tables; and nft ruleset. It does not enter/create namespaces, expose a shell/IPC endpoint, start a service, or mutate network state. It compares the prepared boot UUID and target netns device/inode against `/proc/self/ns/net` before and after each command and rejects the PID 1 namespace. Exit/stderr/timeout/size/JSON/identity failures invalidate the capture. Raw feeds and a manifest are written only after a complete parse; the manifest explicitly records no atomicity and no ownership proof. The collector has not run on a live VM.

The `-4/-6` command context supplies family for iproute2 JSON rules such as the standard `src: all` local/main/default rules, whose records can omit `family`. `srclen`/`dstlen` are combined with address selectors, and contradictory family/address data fails closed. The direct fixture parser still rejects addressless records without a trusted command family. Unknown nft entities, unsupported route shapes, and other unrecognized data fail the entire snapshot. Six sequential commands still cannot prove an atomic kernel snapshot or creation continuity.

## Future Linux backend boundary

`backend/app/network_agent/linux_inventory.py` provides a read-only `InventoryReader` protocol and a strict parser for link, rule, route and nft JSON. All four logical feeds must be supplied; malformed JSON, duplicate keys, unsupported fields/entities, ambiguous address family, missing parent nft table/chain, duplicate interface identity, or a route referencing an absent link fails closed. Unsupported multipath/nexthop/encapsulation routes fail closed. The parser accepts a namespace identity tuple (boot UUID, netns device/inode) in addition to its display name, binds observed IDs to it, and stores it on the snapshot. The collector independently verifies these values against the prepared target; the display name alone is not evidence.

Observed resource keys are built from parsed fields. nft tables use family+table, chains family+table+chain, and rules family+table+chain+handle. Routes use family, table, destination, source, TOS, metric, type, scope, protocol and preference. Rules retain priority, selectors, fwmark/mask and table. Links retain both name and ifindex. `reject_unproven_desired` requires the expected trusted namespace identity and checks exact claims, nft parent occupancy, foreign route occupancy in a requested table or route destination/table slot, and overlapping rule marks/masks. It never supplies a proof or adopts an observed object. `compare_agent_receipts` rejects all nonempty protected receipt sets because the fixture parser has no creation-continuity proof. Desired `NetworkObject` is still a separate Agent-validated request model; this parser does not accept Control Plane supplied encoded kernel keys as observations. The fixture `revision` is a content digest for comparison, **not** an atomic kernel generation/CAS token.

This parser recognizes a deliberately narrow subset of iproute2/nft JSON. It must be extended with versioned fixtures and tests before accepting other output shapes. In particular nft sets/maps/flowtables/stateful objects, route multipath/`nhid`/encapsulation, and unrecognized identity fields produce an error rather than a partial-success snapshot. Rule expressions are retained for drift detection, but dynamic counters may change a fingerprint; a later live reader must normalize benign volatile fields only after proving which fields cannot affect ownership. No parser success proves six separate Linux commands observed one atomic instant.

After a restart, nft rule handles, interface names/ifindexes, routing table IDs, route selectors, rule priorities and fwmarks can be reused or recreated. An nft table/chain name can likewise be replaced. None carries an Agent-authenticated creation identity. The same namespace inode can be reused after the original namespace disappears; boot identity reduces cross-boot confusion but does not prove lifetime. These entities cannot be safely recovered as Agent-owned from a snapshot, `tempest-*` name, handle, ifindex or matching fingerprint alone. A protected creation receipt and verified continuity are required. If continuity cannot be established, report an unresolved foreign/ambiguous object and do not mutate it. The fixture backend intentionally has no receipt-loading or proof-minting API.

The Linux backend should offer a complete typed inventory snapshot with revision/consistency evidence and exact-object operations guarded by fresh ownership checks. It must reject partial enumeration and ambiguous nft handles, route selectors, priorities, marks, table IDs, or interface identities. An interface name or routing table ID may be reused by another process; the backend cannot adopt it without the protected receipt and matching live evidence. Deletion must re-read the exact object immediately before mutation and abort on mismatch. Never issue global nft flush, `ip route flush`, broad table/rule deletion, default-route replacement, or an operation outside the prepared namespace. These are design requirements only; no Linux backend exists in this slice.

Future Stage should validate registry claims and persist a candidate diff without mutation. Apply should revalidate a complete inventory, persist pending intent, then perform exact-object changes with per-object checks and compensation. Verify should observe actual owned resources and detect drift before Confirm. Confirm should bind the verified generation to last-known-good receipts. Rollback must recheck ownership of each object before restoring or deleting it; if evidence is lost, preserve the object and protected-ingress deny state and report degraded status. Those transactional and network operations belong to 2.6 and have not been implemented.

Durable state needed before runtime use includes namespace identity/inode and boot identity, generation UUID/number and CAS base, canonical plan/object fingerprints, typed claims, independently minted creation receipts and kernel selectors, pending diff/deadline, verified status, and last-known-good snapshot. The journal must be writable only by Agent and survive a process restart. Recovery after reboot and reconciliation of recycled kernel handles require Linux VM tests and remain open.
