# PiTun → TEMPEST — матрица требований

Сопоставление [спецификации](PROJECT_SPEC.md) с [исходным SHA PiTun](UPSTREAM_BASELINE.md). **Есть** означает наличие пути в upstream-коде, **частично** — переиспользуемую основу с разрывом в целевом сценарии, **нет** — отсутствие продуктового пути. Сетевые возможности оценены статически, с отдельными unit-проверками.

В закреплённом [Xray-core 26.10.31](https://github.com/XTLS/Xray-core/blob/v26.10.31/infra/conf/xray.go#L25) движок регистрирует `wireguard` и `vless` inbounds, а также `tun`. Наличие загрузчика в Xray подтверждает возможность исследовать адаптер. PiTun эти VPN inbounds в локальном dataplane не конфигурирует. Комментарий PiTun о TUN как функции только sing-box расходится с закреплённой версией: поля PiTun `inet4Address`, `autoRoute`, `strictRoute`, `stack` не совпадают с [Xray TunConfig](https://github.com/XTLS/Xray-core/blob/v26.10.31/infra/conf/tun.go#L15), где, например, есть `gateway` и `autoSystemRoutingTable`. Поведение текущего JSON, последствия для маршрутов и выбор адаптера остаются предметом проверки на VM.

Для MVP переиспользуемы FastAPI/React/SQLite, Node CRUD, подписки, Xray генерация, правила и диагностика. Главные разрывы на критическом пути — изоляция API, локальный WG ingress, управляемая привязка клиента к egress, fail-closed для IPv4/IPv6/DNS и проверяемый rollback. Полноценный router, DHCP/AP, SSH provisioning и управление x-ui в этот путь не входят.
